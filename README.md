## ⚠️ ข้อจำกัดของรุ่นนี้ — อ่านก่อนใช้งาน

รุ่นนี้เป็น MVP ที่ตัดหลายอย่างออกโดยเจตนาเพื่อให้เห็นโครงข้อมูลหลักทำงานได้ก่อน ข้อจำกัดต่อไปนี้ไม่ใช่ bug แต่เป็นสิ่งที่ยังไม่ได้ทำ

### 1. ข้อมูลอยู่แค่ในเบราว์เซอร์ของคุณเท่านั้น

ระบบเก็บข้อมูลใน `localStorage` ของเบราว์เซอร์ ไม่มี server และไม่มีฐานข้อมูล ผลที่ตามมา:

- **ทีมแชร์ข้อมูลกันไม่ได้** — สิ่งที่คุณสร้างไม่มีใครอื่นเห็น และคุณไม่เห็นของคนอื่น
- เปิดจากเครื่องอื่นหรือเบราว์เซอร์อื่นจะไม่เห็นข้อมูลเดิม
- **ล้าง browser data แล้วข้อมูลหายถาวร** กู้คืนไม่ได้
- ใช้ปุ่ม **Export** เก็บไฟล์สำรองไว้เป็นระยะ และ **Import** เพื่อกู้คืนหรือย้ายเครื่อง

### 2. ไม่มีระบบยืนยันตัวตน

การเลือกชื่อจาก dropdown มุมล่างซ้าย **ไม่ใช่การเข้าสู่ระบบ** — เป็นเพียงการเลือกว่าจะบันทึกชื่อใครเป็นผู้รับผิดชอบหรือผู้รายงาน ผลที่ตามมา:

- ใครก็แก้หรือลบข้อมูลของใครได้ทั้งหมด
- ใครก็ระบุชื่อคนอื่นเป็นผู้รับผิดชอบหรือผู้รายงานได้

> **ห้ามนำข้อมูลจากรุ่นนี้ไปคำนวณ KPI รายคน** เพราะชื่อผู้รับผิดชอบและผู้รายงานไม่มีความน่าเชื่อถือ ใครก็กรอกชื่อคนอื่นได้ การใช้ข้อมูลนี้ประเมินคนจะทำให้ผลผิดพลาดและไม่ยุติธรรม

### 3. ยังไม่มีในรุ่นนี้

KPI Dashboard · Dual Estimate (auto-rollup) · Evidence form บังคับ 3 ส่วน · NFR Metric validation · Status workflow · Sprint Management · Multi-Project · ประวัติการแก้ไข · การใช้งานบนมือถือ · การลากการ์ดข้าม column

```bash

# รันในโหมดพัฒนา แล้วเปิด http://localhost:5173

npm run preview
```

## สิ่งที่ทำได้ในรุ่นนี้

### Requirements
สร้าง อ่าน แก้ ลบ Requirement โดยบังคับระบุประเภท (Functional / Non-Functional) และระดับความสำคัญแบบ MoSCoW (ค่าเริ่มต้น Should) · Board จัดกลุ่มตาม MoSCoW · Requirement ที่ยังไม่มี Task จะมีเครื่องหมายเตือน

### Tasks
สร้าง อ่าน แก้ ลบ Task โดย**บังคับผูกกับ Requirement** และบังคับระบุตำแหน่งผู้รับผิดชอบ (SA / UX / Dev / Tester) · Board จัดกลุ่มตามตำแหน่ง ทำให้เห็นภาระงานของแต่ละตำแหน่ง · กรองได้ตามผู้รับผิดชอบ ตำแหน่ง และ Requirement ต้นทาง

### Defects
สร้าง อ่าน แก้ ลบ Defect โดย**บังคับผูกกับ Task** บังคับระบุประเภทจาก 5 ค่า (Code Bug / SA Gap / Design Gap / Test Escape / NFR Violation) และบังคับระบุความรุนแรง · Board จัดกลุ่มตามประเภท ตัวเลขบนหัว column คือจำนวน defect แยกตามประเภท

**เหตุผลที่แยก 5 ประเภท:** ปัญหาไม่ได้เกิดจากโค้ดเสมอไป การแยกประเภททำให้เห็นว่าต้นน้ำอยู่ที่ใด — สเปคไม่ครบ (SA Gap), design ไม่ครอบ (Design Gap), โค้ดผิด (Code Bug), test ปล่อยผ่าน (Test Escape), หรือไม่ผ่านเกณฑ์ที่วัดได้ (NFR Violation) ถ้า SA Gap สูง แปลว่าต้องแก้ที่การเขียนสเปค ไม่ใช่โทษคนเขียนโค้ด

### สายเชื่อมโยง
- จาก Requirement เห็น Task และ Defect ทั้งหมดที่อยู่ใต้มัน
- จาก Defect ย้อนขึ้นถึง Task และ Requirement ต้นทาง
- ก่อนลบสิ่งที่มีลูก ระบบบอกจำนวนที่จะถูกลบตามไปด้วย

### Export / Import
บันทึกข้อมูลทั้งหมดเป็นไฟล์ JSON และนำกลับเข้ามาได้ ไฟล์ที่รูปแบบไม่ถูกต้องจะถูกปฏิเสธก่อนเขียนทับ ข้อมูลเดิมจึงไม่เสีย

## โครงสร้างโค้ด

```
src/
├── styles/          ค่าสี ระยะห่าง ตัวอักษร (design tokens)
├── shared/          พื้นที่ร่วม — แก้ต้องตกลงกันก่อน
│   ├── types.ts     type และค่า enum ของทั้ง 3 entity
│   ├── storage.ts   คุยกับ localStorage
│   ├── repository.ts CRUD ทั่วไป
│   ├── traceability.ts ตรรกะสายเชื่อมโยง
│   └── components/  component ที่ทั้ง 3 module ใช้ร่วมกัน
└── modules/
    ├── requirements/  ทีม A
    ├── tasks/         ทีม B
    └── defects/       ทีม C
```

**กฎการแบ่งงาน:** `src/shared/` และ `src/styles/` เป็นพื้นที่ร่วม ต้องนิ่งก่อนทั้ง 3 ทีมเริ่มงาน หลังจากนั้นแต่ละทีมแตะแค่โฟลเดอร์ module ของตัวเอง เพื่อลด merge conflict
