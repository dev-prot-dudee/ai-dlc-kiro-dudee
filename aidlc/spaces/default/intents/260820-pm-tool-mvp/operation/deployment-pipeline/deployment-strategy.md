# Deployment Strategy — PM Tool MVP

ที่มา: `cd-config.md` (ทรัพยากรและ script ที่ใช้), `build-and-test/build-test-results.md` (เกณฑ์คุณภาพที่ผ่านจริง), `build-and-test/build-instructions.md` (ขั้นตอน build), `requirements.md` (NFR และความเสี่ยง)

รายการ upstream ที่ไม่มี — `ci-config`, `quality-gates`, `infrastructure-specification`, `cicd-pipeline` — อธิบายไว้ใน `cd-config.md` หัวข้อแรก โดยสรุปคือ `express` ข้ามขั้นที่ผลิตทั้งสี่โดยการออกแบบ

## กลยุทธ์ที่เลือก: replace ตรง ๆ พร้อม cache ที่ตั้งถูก

**ไม่ใช้ blue/green และไม่ใช้ canary** เหตุผล:

| กลยุทธ์ | ทำไมไม่เลือก |
|--------|-------------|
| Blue/Green | ต้องมี distribution หรือ origin สองชุดแล้วสลับ · ระบบนี้ไม่มี state ฝั่ง server ให้ต้องระวังตอนสลับ (ข้อมูลอยู่ในเบราว์เซอร์ผู้ใช้) ความซับซ้อนที่เพิ่มไม่ได้ซื้ออะไรกลับมา |
| Canary | ต้องแบ่ง traffic ตามสัดส่วน ซึ่ง CloudFront ทำได้ด้วย Lambda@Edge แต่ต้องเขียนโค้ดและมี metric ให้ดูว่ากลุ่มทดลองแย่กว่าหรือไม่ · รุ่นนี้ยังไม่มี observability ที่จะบอกได้ (ขั้น observability-setup ยังไม่รัน) canary ที่ไม่มี metric คือการเดา |
| **Replace ตรง ๆ** | static file ทั้งก้อน 67 KB อัปโหลดเสร็จในไม่กี่วินาที ความเสี่ยงต่ำ ย้อนกลับเร็ว และ versioning ของ S3 เก็บของเก่าไว้ให้อยู่แล้ว |

สิ่งที่ทำให้ replace ปลอดภัยพอไม่ใช่โชค แต่เป็นสามอย่างนี้:

1. **assets มี hash ในชื่อไฟล์** — เวอร์ชันเก่าและใหม่อยู่ร่วมกันบน S3 ได้ ผู้ใช้ที่เปิดหน้าไว้ก่อน deploy ยังโหลดไฟล์เดิมได้ต่อ ไม่พังกลางทาง
2. **อัปโหลด assets ก่อน `index.html`** — ไม่มีช่วงที่ `index.html` ชี้ไปยังไฟล์ที่ยังไม่ขึ้น
3. **`index.html` ไม่ถูก cache** — ผู้ใช้เห็นเวอร์ชันใหม่ทันทีที่ refresh ไม่ต้องรอ cache หมดอายุ

## ลำดับการปล่อยของ

```
1. ตรวจคุณภาพ 4 ด่าน        ← ล้มที่นี่ = ไม่มีอะไรขึ้น production
2. build                      ← ล้มที่นี่ = ไม่มีอะไรขึ้น production
3. อัปโหลด assets (cache 1 ปี)
4. อัปโหลด index.html (ห้าม cache)
5. invalidate /index.html และ /
6. ตรวจด้วยตา 3 ข้อ
```

ขั้นที่ 1 กับ 2 อยู่ก่อนการแตะ production ทั้งหมดโดยเจตนา — `deploy.sh` ใช้ `set -e` ทำให้หยุดทันทีเมื่อด่านใดล้ม

## การตรวจหลัง deploy — สามข้อ อย่าข้าม

| # | ตรวจอะไร | ถ้าไม่ผ่านแปลว่า |
|---|---------|-----------------|
| 1 | เปิดหน้าแรกแล้วเห็นหน้า Requirements | ไฟล์ไม่ขึ้น หรือ `base` ผิด |
| 2 | เปิด `/tasks` ตรง ๆ แล้ว refresh ต้องไม่ขึ้น 404 | **custom error response ของ CloudFront หลุด** — ต้องมีทั้ง 403 และ 404 เพราะ S3 + OAC ตอบ 403 ไม่ใช่ 404 |
| 3 | สร้าง Requirement แล้ว refresh ข้อมูลยังอยู่ | `localStorage` ถูกบล็อกในเบราว์เซอร์นั้น |

ข้อ 2 เป็นข้อที่พลาดบ่อยที่สุดและเป็นสิ่งแรกที่คนอื่นจะเจอเวลาคุณส่งลิงก์หน้า Tasks ให้ดู

## Environment

รุ่นนี้มี **environment เดียว** ไม่มี staging

เหตุผล: ระบบไม่มี backend ไม่มีฐานข้อมูล ไม่มี integration กับระบบอื่น สิ่งที่ staging มักใช้ตรวจ — schema migration, config ของ service, การต่อกับระบบภายนอก — ไม่มีอยู่ในรุ่นนี้เลย และ e2e 49 scenario ครอบเส้นทางผู้ใช้ในระดับที่ staging จะให้ได้

ถ้าจะเพิ่ม staging ภายหลัง: สร้าง bucket + distribution อีกชุดแล้วส่งค่าตัวแปรต่างกัน **ไม่ต้องแก้ script**

## การจำกัดผู้เข้าถึง — เรื่องที่ควรตัดสินใจก่อนส่ง URL ให้ใคร

แอปไม่มีระบบยืนยันตัวตน (ความเสี่ยง R1) URL ที่ได้จาก CloudFront เปิดให้ใครก็เข้าได้

**ตัวเลือกบน AWS** เรียงจากง่ายไปยาก:

| วิธี | กันได้แค่ไหน | ต้นทุน |
|-----|-------------|--------|
| **CloudFront Functions ทำ basic auth** | กันคนที่ไม่รู้ user/password · เหมาะกับ demo ภายใน | เขียน function สั้น ๆ ไม่กี่บรรทัด |
| **AWS WAF จำกัด IP** | ให้เข้าได้แค่จาก IP ที่ระบุ เช่น IP ออฟฟิศ | ต้องรู้ช่วง IP และมีค่าใช้จ่ายของ WAF |
| **CloudFront signed URL** | ให้ลิงก์ที่หมดอายุได้ | ซับซ้อนกว่า ต้องมีตัวออกลิงก์ |

**ทั้งสามวิธีไม่ใช่ระบบ auth จริง** และไม่แก้ปัญหาว่าใครที่เข้าถึงได้ก็แก้ลบข้อมูลของตัวเองได้ทั้งหมด — มันแค่กันคนนอกไม่ให้เข้ามาถึงหน้าแอป

ถ้ายังไม่ตั้งอะไรเลย ควรถือว่า URL นี้เป็นความลับที่บอกกันในทีมเท่านั้น และ**ห้ามนำข้อมูลไปคำนวณ KPI รายคน** ตามที่เขียนไว้ใน `README.md`

## NFR ที่ยังไม่มีหลักฐาน — ควรวัดหลัง deploy ครั้งแรก

การ deploy จริงเปิดโอกาสวัดสองข้อที่ค้างอยู่ตั้งแต่ขั้น Build and Test

| NFR | วิธีวัดเมื่อมี URL จริงแล้ว |
|-----|--------------------------|
| **NFR1** FCP ≤ 1.5 วินาที | รัน Lighthouse บน URL ของ CloudFront · การวัดผ่าน CDN จริงมีความหมายมากกว่าวัดบน localhost |
| **NFR4** Chrome / Firefox / Safari | ทำการตรวจ 3 ข้อข้างบนในทั้งสามเบราว์เซอร์ · **จุดเสี่ยงสุดคือ Safari** เพราะจำกัด `localStorage` เข้มกว่าที่อื่น และโหมดส่วนตัวของ Safari อาจทำให้ใช้งานไม่ได้เลย |

ทั้งสองข้อยังไม่มีตัวเลขแม้แต่ตัวเดียว ไม่ควรถือว่าผ่านเพราะ bundle เล็ก — bundle 67 KB ทำให้ NFR1 มีโอกาสผ่านสูง แต่โอกาสสูงไม่ใช่หลักฐาน

## ความเสี่ยงของการ deploy เอง

| ความเสี่ยง | ผลถ้าเกิด | การป้องกันที่มีอยู่ |
|-----------|----------|-------------------|
| ตั้ง cache `index.html` ผิดเป็นแบบยาว | ผู้ใช้ติดเวอร์ชันเก่าจนจอขาว และแก้ยากเพราะต้องรอ cache หมดอายุ | `deploy.sh` ตั้ง `no-cache` ให้ตายตัว ไม่ต้องจำ |
| ลืม invalidate | ผู้ใช้ยังเห็นของเก่าชั่วคราว | `deploy.sh` invalidate ให้อัตโนมัติ |
| `--delete` ลบไฟล์ที่ยังมีคนใช้ | ผู้ใช้ที่เปิดหน้าไว้ก่อน deploy โหลด asset ไม่ได้ | assets มี hash และ S3 เปิด versioning · ความเสี่ยงจำกัดอยู่แค่คนที่เปิดค้างไว้ตอน deploy พอดี ซึ่งกด refresh แล้วหาย |
| deploy ของที่ test ไม่ผ่าน | ของเสียขึ้น production | 4 ด่านอยู่ก่อนการแตะ production และ `set -e` หยุดทันที |
| ชื่อ bucket ซ้ำกับคนอื่นทั้ง AWS | `bootstrap.sh` ล้มตอนสร้าง | script รายงาน error ตรง ๆ ให้เปลี่ยนชื่อ ไม่มีอะไรเสียหาย |
