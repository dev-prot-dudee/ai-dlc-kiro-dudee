# Build and Test Summary — PM Tool MVP

สรุปสถานะความพร้อมของโปรเจกต์หลังผ่านขั้น build-and-test

ที่มา: `code-generation-plan.md` (แผนและเกณฑ์ที่ตกลงไว้), `unit-test-instructions.md` (คำสั่ง test ที่รัน), `code-summary.md` (สิ่งที่ code-generation ส่งมอบและสิ่งที่ยกมาให้ขั้นนี้)

## ข้อกำหนดก่อน build

ต้องมีอย่างเดียวคือ **Node.js 18 ขึ้นไป**

ไม่ต้องมีฐานข้อมูล ไม่ต้องมี Docker ไม่ต้องมี service ภายนอก ไม่ต้องมี environment variable ไม่ต้องมี credential เพราะรุ่นนี้เป็น frontend ล้วนที่เก็บข้อมูลใน `localStorage` (constraint C1)

ข้อดีคือคนใหม่ในทีมเริ่มงานได้ด้วยสองคำสั่ง (`npm install` แล้ว `npm run dev`) ข้อเสียคือทีมแชร์ข้อมูลกันไม่ได้เลย ซึ่งเป็นความเสี่ยง R2 ที่ยังอยู่

| ไฟล์ | สร้างหรือไม่ | เหตุผล |
|------|-------------|--------|
| `build-instructions.md` | ✅ สร้าง | บังคับทุก strategy |
| `integration-test-instructions.md` | ❌ ไม่สร้าง | Minimal ไม่กำหนด และรุ่นนี้ไม่มีขอบเขตระหว่างระบบให้ integrate — ไม่มี backend ไม่มี API ไม่มี service ภายนอก การเชื่อมต่อเดียวที่มีคือ `localStorage` ซึ่ง `storage.spec.ts` ครอบไว้แล้ว 7 scenario |
| `performance-test-instructions.md` | ✅ **สร้าง (เพิ่มจากที่ Minimal กำหนด)** | NFR2 และ NFR3 มีเกณฑ์ที่วัดได้ (≤ 200 ms, 500 รายการ) และ `code-summary.md` ระบุว่ายังไม่ได้วัด การปล่อยผ่านโดยไม่วัดคือการเดา — stage เปิดช่องให้เพิ่ม test type ได้เมื่อบริบทเรียกร้อง |

## ข้อค้นพบสำคัญของขั้นนี้

**จับได้ว่าการวัดผลชุดแรกไม่มีความหมาย** — วัด render board 500 รายการได้ 2.43 ms ซึ่งเร็วเกินกว่าที่จะเป็นไปได้ ตรวจแล้วพบว่า board render การ์ดได้ **0 ใบ** เพราะเขียนข้อมูลทดสอบใน `beforeAll` แต่ `test-setup.ts` ล้าง localStorage ใน `beforeEach` ที่รันทีหลัง

ถ้าปล่อยไว้จะได้ test ที่ผ่านทุกครั้งโดยไม่ได้วัดอะไรเลย ซึ่งผิด guardrail ของ Construction ตรงๆ

แก้แล้วสองชั้น — ย้ายการเขียนข้อมูลไป `beforeEach` และ**เพิ่ม assertion นับ element ที่ render จริงในทุกการวัด** เพื่อให้การวัดที่ว่างเปล่าล้มทันทีในอนาคต ตัวเลขที่ถูกต้องคือ 67–87 ms

ข้อผิดพลาดที่สองในลักษณะเดียวกันคือ `traceForward` ถูกเรียกด้วย object แทน id ทำให้ไม่เคย match อะไรเลยแต่ให้ตัวเลขที่ดูปกติ typecheck จับได้

## ข้อจำกัดและสิ่งที่ยังค้าง

### ยังไม่มีหลักฐาน — ต้องทำด้วยมือ

| NFR | ต้องทำอะไร |
|-----|-----------|
| **NFR1** FCP ≤ 1.5 วินาที | ติดตั้งแล้วรัน Lighthouse บน `npm run preview` |
| **NFR4** Chrome / Firefox / Safari | ทำรายการตรวจ 7 ข้อจาก `build-instructions.md` ในทั้งสามเบราว์เซอร์ |

**จุดที่เสี่ยงที่สุดคือ Safari** เพราะจำกัด localStorage เข้มกว่าเบราว์เซอร์อื่น และระบบนี้พึ่ง localStorage ทั้งหมด ควรตรวจโหมดส่วนตัวด้วย

### วัดแล้วบางส่วน

- **NFR2** วัดงาน JavaScript ครบแล้วและผ่าน แต่ไม่รวม layout กับ paint เพราะ jsdom ไม่มี
- **NFR5** ส่วนที่ทดสอบด้วยโค้ดได้ผ่านแล้ว 11 scenario (หัว column แสดงตัวอักษรไม่ใช่แค่สี, keyboard, label, dialog) แต่ค่า contrast ratio ยังไม่ได้วัดด้วยเครื่องมือ

### ข้อสังเกตด้านความเร็วที่ควรจับตา

ตรรกะทั้งหมดใช้เวลาระดับหลักหน่วย ms แต่ **การ render board ใช้ 67–87 ms คือราว 40% ของงบ 200 ms** และยังไม่รวม paint

คอขวดอยู่ที่ **จำนวน DOM node ไม่ใช่ตรรกะ** ถ้าข้อมูลโตเกิน 500 รายการต่อ entity ทางแก้คือลดจำนวนการ์ดที่ render พร้อมกัน (virtual scrolling หรือแบ่งหน้า) ไม่ใช่ไปปรับตรรกะให้เร็วขึ้น

### ความเสี่ยงที่ยังอยู่ไม่เปลี่ยน

| ความเสี่ยง | สถานะ |
|-----------|-------|
| **R1 ไม่มี auth** | ใครก็แก้ลบข้อมูลของใครได้ และกรอกชื่อคนอื่นเป็นผู้รับผิดชอบได้ · **ห้ามนำข้อมูลไปคำนวณ KPI รายคน** |
| **R2 localStorage** | ทีมแชร์ข้อมูลกันไม่ได้ · บรรเทาบางส่วนด้วย export/import |
| **R3 ตัด evidence และ NFR validation** | เป็นงานรุ่นถัดไป |
| **R4 12 คนแก้ไฟล์ทับกัน** | บรรเทาด้วยโครง `shared/` + `modules/<ทีม>/` แต่ `shared/` ยังเป็นคอขวด |
