## ทำไมมีไฟล์นี้ทั้งที่ Test Strategy เป็น Minimal

Minimal strategy ปกติไม่สร้างไฟล์ test instruction เพิ่ม แต่ขั้นตอนของ stage เปิดช่องไว้ว่า "สร้าง test type เพิ่มได้ทุกระดับ strategy ถ้าบริบทเรียกร้อง"

บริบทที่เรียกร้องในกรณีนี้ชัดเจน: `code-summary.md` ปิดท้ายด้วยการระบุว่า **NFR2 และ NFR3 ยังไม่ได้วัดด้วยตัวเลขจริง** และ NFR ทั้งสองข้อมีเกณฑ์ที่วัดได้ (≤ 200 ms, 500 รายการ) การปล่อยผ่านโดยไม่วัดคือการเดา ซึ่งขัดกับข้อกำหนดของ inception ที่ว่าทุก requirement ต้องมีเกณฑ์ผ่าน/ไม่ผ่านที่ตรวจได้

## ขอบเขตและข้อจำกัดของการวัดนี้ — อ่านก่อนเชื่อตัวเลข

การวัดรันบน **jsdom ไม่ใช่เบราว์เซอร์จริง** ผลที่ตามมา:

| วัดได้ | วัดไม่ได้ |
|--------|----------|
| งานฝั่ง JavaScript — การอ่านเขียน storage, การกรอง, การจัดกลุ่ม, การไล่สายเชื่อมโยง, การสร้าง DOM node | เวลา layout และ paint (jsdom ไม่มี layout engine) |
| อัลกอริทึมที่ระเบิดตามจำนวนข้อมูล เช่นการวนซ้อนที่กลายเป็น O(n²) | เวลาที่ผู้ใช้เห็นภาพเปลี่ยนจริง |
| จำนวน element ที่ออกมาจริง | ผลของ CSS ที่ซับซ้อน, การ scroll, การ reflow |

**ตัวเลขที่ได้จึงเป็นขอบล่างของเวลาจริง ไม่ใช่ค่าที่ผู้ใช้จะเจอ** ใช้สรุปได้อย่างเดียวคือ "ไม่มีอัลกอริทึมที่ระเบิดตามจำนวนข้อมูล" ซึ่งเป็นความเสี่ยงหลักที่ระดับ 500 รายการ ถ้างาน JS ล้วนยังเกิน 200 ms แล้ว ในเบราว์เซอร์จริงย่อมเกินแน่นอน — แต่ผ่านในนี้ยังไม่การันตีว่าผ่านในเบราว์เซอร์

**NFR1 (FCP ≤ 1.5 วินาที) วัดในนี้ไม่ได้เลย** เพราะ First Contentful Paint เป็นเหตุการณ์ของ paint ที่ jsdom ไม่มี ต้องวัดด้วย Lighthouse ในเบราว์เซอร์จริง — ดูหัวข้อท้ายไฟล์

## วิธีรัน

```bash
npm run test:perf
```

หรือระบุไฟล์ตรงๆ:

```bash
npx vitest run src/perf
```

ตัวเลขที่วัดได้จะพิมพ์ออกมาทาง stderr ด้วยคำนำหน้า `[วัดผล]` และจำนวน element ที่ตรวจได้ด้วยคำนำหน้า `[ตรวจ]`

**ไม่รวมอยู่ใน `npm test`** โดยเจตนา เพราะ `npm test` ต้องให้ผลเหมือนกันทุกครั้งเพื่อใช้เป็นเกณฑ์ merge ส่วนการวัดเวลาแปรผันตามเครื่องและภาระงานขณะนั้น ถ้าเอามารวมกันจะได้ CI ที่ล้มเป็นครั้งคราวโดยที่โค้ดไม่ได้ผิด

## ข้อมูลที่ใช้ทดสอบ

`src/perf/nfr-performance.spec.tsx` สร้างข้อมูล **500 รายการต่อ entity รวม 1,500 รายการ** ที่เชื่อมโยงกันจริง ไม่ใช่ข้อมูลลอยๆ:

- Requirement 500 ตัว กระจายทั้ง 4 ระดับ MoSCoW
- Task 500 ตัว ผูกกับ Requirement 400 ตัวแรก — **เจตนาให้เหลือ Requirement 100 ตัวที่ไม่มี Task** เพื่อให้ตรรกะ FR4.3 ต้องทำงานที่ปริมาณจริง
- Defect 500 ตัว ผูกกับ Task 450 ตัวแรก กระจายทั้ง 5 ประเภทและ 4 ระดับความรุนแรง

## กฎที่ต้องรักษาเมื่อแก้ไฟล์วัดผล

### 1. เขียนข้อมูลใน `beforeEach` ห้ามใช้ `beforeAll`

`src/test-setup.ts` ล้าง localStorage ใน `beforeEach` ซึ่งลงทะเบียนไว้ก่อน hook ของไฟล์ test จึงรันก่อนเสมอ ถ้าเขียนข้อมูลใน `beforeAll` ข้อมูลจะถูกล้างก่อน test เริ่ม

**เรื่องนี้เกิดขึ้นจริงในการวัดครั้งแรกของ stage นี้** — วัด board ได้ 2.43 ms ซึ่งเร็วเกินจริงจนน่าสงสัย ตรวจแล้วพบว่า render การ์ดได้ **0 ใบ** การวัดผ่านเกณฑ์ทุกข้อโดยไม่ได้วัดอะไรเลย

### 2. ทุกการวัดต้องมี assertion ยืนยันว่างานเกิดขึ้นจริง

board ที่ render ศูนย์การ์ดเร็วเสมอ การกรองที่ไม่ match อะไรเร็วเสมอ ดังนั้นทุก test ต้องมีคู่กัน:

```ts
expect(cards).toBe(N);              // งานเกิดขึ้นจริง
expect(elapsed).toBeLessThan(200);  // และเร็วพอ
```

ถ้ามีแต่บรรทัดที่สอง test นั้นไม่มีค่าใดๆ และผิด guardrail ของ Construction ที่ห้ามสร้าง test ที่ผ่านโดยไม่สนใจว่า implementation ถูกหรือไม่

### 3. ใช้ค่ากลางจากหลายรอบ ไม่ใช่ค่าจากรอบเดียว

ฟังก์ชัน `measure()` warm-up หนึ่งครั้งก่อน (เลี่ยงผลของ JIT) แล้ววัดซ้ำ 3–5 รอบ เอาค่ากลาง ค่าจากรอบเดียวแกว่งได้เป็นสิบเท่าเมื่อ GC ทำงานพอดี

## เกณฑ์และผลที่วัดได้

วัดบน macOS, Node 25.9.0, jsdom, 2026-08-20

| สิ่งที่วัด | งบ | วัดได้ | ผล |
|-----------|-----|-------|-----|
| เขียน 1,500 รายการลง localStorage | 200 ms | **0.88 ms** | ผ่าน |
| ขนาดข้อมูล 1,500 รายการ | < 2.5 MB | **276.4 KB** | ผ่าน |
| `traceForward` × 500 (FR4.1) | 200 ms | **8.14 ms** | ผ่าน |
| `traceBackward` × 500 (FR4.2) | 200 ms | **2.03 ms** | ผ่าน |
| `findRequirementsWithoutTasks` (FR4.3) | 200 ms | **0.05 ms** | ผ่าน |
| `countDefectsByType` (FR3.7) | 200 ms | **0.04 ms** | ผ่าน |
| render Requirements board 500 การ์ด | 200 ms | **87.15 ms** | ผ่าน |
| render Tasks board 500 การ์ด | 200 ms | **67.64 ms** | ผ่าน |
| render Defects board 500 การ์ด | 200 ms | **69.16 ms** | ผ่าน |

**ข้อสังเกตที่ควรจับตา:** ตรรกะสายเชื่อมโยงใช้เวลาระดับหลักหน่วย ms แต่ **การ render board ใช้ 67–87 ms คือประมาณ 40% ของงบทั้งก้อน** และนี่ยังไม่รวม layout กับ paint ที่ jsdom วัดไม่ได้ ในเบราว์เซอร์จริงตัวเลขนี้จะสูงกว่านี้

แปลว่าคอขวดอยู่ที่ **จำนวน DOM node ไม่ใช่ตรรกะ** ถ้าข้อมูลโตเกิน 500 รายการต่อ entity ทางแก้คือลดจำนวนการ์ดที่ render พร้อมกัน (virtual scrolling หรือแบ่งหน้า) ไม่ใช่การไปปรับตรรกะให้เร็วขึ้น เพราะตรรกะไม่ใช่ปัญหา

## สิ่งที่ยังต้องวัดในเบราว์เซอร์จริง

การวัดข้างบนไม่ครอบสามเรื่องนี้ ต้องทำด้วยมือ

### NFR1 — FCP ≤ 1.5 วินาที

```bash
npm run build
npm run preview
```

แล้วรัน Lighthouse (ยังไม่ได้ติดตั้งในโปรเจกต์ ต้องติดตั้งก่อนหรือใช้ที่ฝังใน Chrome DevTools):

```bash
npx lighthouse http://localhost:4173 --only-categories=performance --view
```

ดูค่า First Contentful Paint เกณฑ์คือ ≤ 1.5 วินาทีบนเครือข่ายปกติ

**การคาดการณ์:** bundle ที่วัดได้คือ 67 KB gzip ซึ่งเป็นเพียง 22% ของงบ 300 KB และไม่มีการเรียก network ตอนเปิดหน้าเลย (ข้อมูลอยู่ใน localStorage) โอกาสผ่านสูงมาก แต่ **ยังไม่ได้วัด จึงยังไม่สรุป**

### NFR2 ในเบราว์เซอร์จริง

เปิด DevTools → Performance แล้วบันทึกช่วงที่:
- พิมพ์ในช่องค้นหา (จุดที่หนักสุดเพราะ re-render ทุกตัวอักษร)
- เปลี่ยนค่าตัวกรอง
- สลับ Board ↔ List

ดู `Total Blocking Time` เกณฑ์คือแต่ละการกระทำ ≤ 200 ms

### NFR4 — Chrome, Firefox, Safari

เปิด `npm run preview` แล้วทำ 7 ข้อในรายการตรวจของ `build-instructions.md` ในทั้งสามเบราว์เซอร์ จุดที่เสี่ยงต่างกันคือ:

| เบราว์เซอร์ | จุดที่ต้องดูเป็นพิเศษ |
|-----------|---------------------|
| Safari | โหมดส่วนตัวของ Safari จำกัด localStorage เข้มกว่าที่อื่น ต้องตรวจว่า error handling ทำงาน |
| Firefox | การจัดกลุ่มด้วย CSS grid ของหัว column |
| Chrome | เป็นตัวอ้างอิงที่พัฒนามาบน |
